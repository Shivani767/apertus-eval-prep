## How to read the core means

Four of the seven models score exactly `0.0000` on the 38-item core suite. That is a
measurement artefact rather than a capability ranking: the harness sends raw text (no chat
template is applied) while the task asks for a single letter, so an answer carrying any
surrounding text is scored wrong. Examples straight from the committed
`scored_examples.jsonl`:

- `microsoft/Phi-3.5-mini-instruct` predicted `# answer b) oak tree…` — the correct letter
  `b` is present, but the extraction reads the first token.
- `HuggingFaceTB/SmolLM3-3B` predicted `the correct answer is c. the human heart's primary
  function is…` — it states the right answer and then explains it.
- `Qwen/Qwen2.5-1.5B-Instruct` predicted `c the primary function of the human heart…` —
  right letter, trailing prose.
- `HuggingFaceTB/SmolLM2-1.7B-Instruct` predicted `None` — a genuine failure on these items.

`google/gemma-2-2b-it` shows the same artefact in a milder form and is the clearest
illustration of it: 8 of 38 core items are scored correct for a core mean of `0.2105`, while
the rest are continuations rather than answers, for example the raw text
`\n**A**\n**B**\n**C**\n**D**\n` for an item whose gold answer is `b`. A model that emitted
the bare letter would score far higher on the identical weights.

The core mean therefore measures terse format compliance as much as correctness. The
suites that tolerate prose are not affected: SmolLM3-3B reaches the highest observed
RAG/agent mean (0.30) in this set while scoring 0.0000 on the letter-only core task.
Changing the protocol (a chat-template variant, or a documented answer-extraction rule)
changes `metric_definition_version` and requires re-running every model, so it is a
protocol decision to record in the deviation log rather than a reporting fix.

## Prompt protocol, and what a re-run will change

The `0.0000` scores above are a prompt-protocol artefact. The `local_transformers` adapter
built the model input as `"{system}\n\n{user}"` and handed it to the tokenizer raw, so an
instruction-tuned model was served like a base model: it continued the passage instead of
replying, and the answer never appeared where the extractor looks. The raw text is preserved
verbatim in each `raw_outputs.jsonl` (for example Gemma's `\n**A**\n**B**\n**C**\n**D**\n`),
which is how the artefact is identifiable rather than merely suspected.

`apply_chat_template` now exists on the adapter and wraps the request in the tokenizer's own
chat format. Every real-model config in `configs/` sets it to `true`, and the choice is
recorded in each run manifest next to the model and revision, because the prompt protocol is
part of the claim. The default stays `false` so existing configurations keep their exact
behaviour, and a run served raw text against a tokenizer that *has* a template records a
warning rather than being silently corrected.

**Consequences for these numbers, stated plainly:**

- The models currently at `0.0000` are not expected to be at `0.0000` after a re-run. Their
  committed scores measure the old protocol and should be read as such.
- Re-running is a **protocol change**, not a re-measurement of the same thing. The prompt
  version and template hash will differ, so these runs are not comparable to their
  replacements and must be replaced, not merged.
- Until the cohort is re-run, the honest summary is: the comparison below is internally
  consistent (same protocol, same identity, so the models are comparable to each other), and
  its absolute values understate every model.

The fix is in `src/apertus_eval_prep/adapters/local_transformers.py` and is covered by
`tests/test_chat_template.py` and `tests/test_chat_template_e2e.py`, which pin the raw
default, the templated path, the manifest field, the warning, and the refusal to fall back
to raw text when a template fails to apply.

## Layout (per model)

`<Model>/` is the notebook's exported run tree, unchanged: `local_baseline/`,
`local_variance/`, `local_rag_agent/`, `local_safety/`, `mock_smoke/`, `study/`,
`configs/`, `comparison_points.json`, `selection.json`, `review_package.jsonl`.
Each run directory keeps the platform's immutable artifacts (`manifest.json`,
`config.resolved.yaml`, `metrics.json`, `confidence_intervals.json`, `gate_report.json`,
`failures.jsonl`, `failure_fingerprint.json`, `scored_examples.jsonl`, `raw_outputs.jsonl`,
`report.md`, `report.html`).

Two derived files are added on top:

- `summary.md` / `summary.json` — generated by `scripts/summarise_real_model_results.py`.
  Do not hand-edit them; a test regenerates the summary and fails if the committed copy
  differs.

## Interpretation rules

- Only `LOCAL_REAL_MODEL` runs support statements about model quality. `mock_smoke/` is
  framework validation, not evidence.
- Two runs are comparable only when `evidence_mode`, `dataset_hash`, `task_hash`,
  `prompt_hash`, `prompt_version` and `metric_definition_version` match. `model_id` and
  its revision are expected to differ when the comparison spans models.
- Latency is client-side wall-clock time on ephemeral Colab hardware; it is not
  production serving latency.
- A `BLOCKED_*` gate is an engineering policy aid, not production approval. Read the
  "Warnings" section of a model's `summary.md` before quoting any number from it.
- Every model directory records the revision it was run against. A revision of `main` is
  not a pinned commit; the run cannot be reproduced exactly from that tree alone.

## Adding a model

1. Generate its notebook: `python3 scripts/build_real_model_notebooks.py` (registry in
   `scripts/build_real_model_notebooks.py`).
2. Run `notebooks/real_model_<slug>.ipynb` in its own Colab account; section 6 exports the
   zip.
3. Extract the zip into `results/colab_real_model/<HF model name>/`.
4. `python3 scripts/summarise_real_model_results.py results/colab_real_model/<HF model name>`
5. Rebuild the reports so every model shares one style (rendering only, no re-inference):
   `python3 scripts/regenerate_colab_reports.py results/colab_real_model/<HF model name>`
6. Commit the run tree plus the generated `summary.json` and `summary.md`.
